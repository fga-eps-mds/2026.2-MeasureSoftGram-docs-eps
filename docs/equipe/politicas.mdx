# Políticas de trabalho

## Política de branches

| Branch | Propósito | Origem | Destino |
| --- | --- | --- | --- |
| `main` | Código estável, publicado | - | - |
| `devel` | Integração do trabalho da sprint | `main` | `main` |
| `feat/<nome>` | Nova funcionalidade | `devel` | `devel` |
| `fix/<nome>` | Correção de defeito | `devel` | `devel` |
| `docs/<nome>` | Alteração de documentação | `devel` | `devel` |

Nomes de branch em minúsculas, palavras separadas por hífen.

## Política de commits

A equipe adota [Conventional Commits](https://www.conventionalcommits.org/):

```
<tipo>(<escopo opcional>): <descricao no imperativo>
```

| Tipo | Uso |
| --- | --- |
| `feat` | Nova funcionalidade |
| `fix` | Correção de defeito |
| `docs` | Somente documentação |
| `test` | Adição ou ajuste de testes |
| `refactor` | Mudança sem alterar comportamento |
| `chore` | Tarefas de manutenção e build |

Commits com mais de um autor devem usar `Co-authored-by:`.

## Política de code review

- Todo Pull Request precisa de aprovação de ao menos um outro integrante.
- O PR deve descrever o que muda e como testar.
- O autor não faz merge do próprio PR sem aprovação.
- A CI precisa estar verde antes do merge.

## Código de conduta

A equipe segue o código de conduta da organização fga-eps-mds. Comportamentos
que violem o código devem ser comunicados aos monitores da disciplina.
